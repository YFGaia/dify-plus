# Dify-Plus 数据库与迁移

本文说明现行二开数据结构、版本链与维护边界。功能语义见[后端说明](./二开功能详解-后端与数据层.md)，部署入口见[部署说明](./二开部署配置与运维说明.md)。

## 两条迁移链

上游迁移位于 `api/migrations/`，扩展迁移位于 `api/migrations_extend/`。两者使用同一应用数据库，分别由 `alembic_version`、`alembic_version_extend` 保存版本。

| 迁移链 | 升级命令 | 范围 |
|---|---|---|
| Dify 上游 | `flask db upgrade` | 原生账号、空间、应用、工作流等结构 |
| Dify-Plus | `flask extend_db upgrade` | 二开额度、应用配置、Casdoor、邀请与实例管理范围 |

[`docker/docker-compose.dify-plus.yaml`](../../docker/docker-compose.dify-plus.yaml) 的迁移服务依次运行两条链。迁移必须只有一个执行者；API/worker 启动前应确认两条链达到源码迁移头。

部署后从 `docker/` 目录检查目标实例：

```bash
docker compose -f docker-compose.dify-plus.yaml exec api flask db current
docker compose -f docker-compose.dify-plus.yaml exec api flask extend_db current
docker compose -f docker-compose.dify-plus.yaml exec api flask extend_db heads
docker compose -f docker-compose.dify-plus.yaml exec api flask extend_db history
```

升级使用 Compose 的单独迁移服务，具体启动顺序见部署说明。开发环境使用 `uv run --project api` 运行后端命令；需要保证 Flask 应用、迁移目录和环境配置均指向 `api/`。

连接配置必须指向目标环境。升级前保存数据库与对象存储备份；不要手工改版本表，也不要以应用启动替代迁移验证。迁移框架按版本执行一次，不能笼统声称所有脚本都支持手工重复执行。

## 现行数据模型

### 额度与使用记录

| 表 | 含义 | 模型文件 |
|---|---|---|
| `account_money_extend` | 总额度、已用额度，`account_id` 唯一 | `api/models/account_money_extend.py` |
| `account_layover_record_extend` | 遗留转发费用明细 | 同上 |
| `account_money_monthly_stat_extend` | 个人月度快照 | `api/models/account_money_monthly_stat_extend.py` |
| `api_token_money_extend` | Key 累计/日/月消费、日/月限额与备注 | `api/models/api_token_money_extend.py` |
| `api_token_money_daily_stat_extend` | Key 日快照 | 同上 |
| `api_token_money_monthly_stat_extend` | Key 月快照 | 同上 |
| `api_token_message_joins_extend` | Key 与消息或工作流运行的费用关联 | 同上 |
| `end_user_account_joins_extend` | 应用 end user 与付费账号关联 | `api/models/model_extend.py` |

费用按 USD 归一。个人 `total_quota` 与 `used_quota` 独立于上游 Cloud 套餐；Key `accumulated_quota` 是累计消费，日/月上限由 `day_limit_quota`、`month_limit_quota` 控制。快照任务先写快照，再在同一事务内清零对应消费字段；累计消费不因周期重置清零。

### 应用、对话与归因

| 表 | 含义 | 模型文件 |
|---|---|---|
| `app_extend` | `retention_number` 记忆轮数、`webapp_auth_enabled` 登录开关 | `api/models/model_extend.py` |
| `message_context_extend` | 会话分段的消息位置和时间 | 同上 |
| `app_statistics_extend` | 应用使用次数 | 同上 |
| `workflow_run_account_extend` | 原始账号、空间与应用范围；匿名账号为 NULL | `api/models/workflow_account_extend.py` |

推荐与安装使用原生 `recommended_apps`、`installed_apps`，分类在 `recommended_apps.categories`。`recommended_category_extend` 与 `recommended_apps_category_join_extend` 不属于现行结构。

运行归因以 `workflow_run_id` 为主键，并有空间/应用/账号范围索引。继续运行者不能覆盖原始账号；没有归因行的历史运行保持未知。

### 实例系统管理

| 表 | 含义 | 模型文件 |
|---|---|---|
| `system_management_scope_extend` | `initialization` 单例引用真实初始化空间 | `api/models/system_management_scope_extend.py` |
| `system_integration_extend` | 钉钉、通用 OAuth2 等集成配置 | `api/models/system_extend.py` |
| `code_execution_control_extend` | 完整执行环境的空间 owner 邮箱名单，邮箱唯一 | 同上 |

管理授权取数据库当前空间与真实角色。初始化关联不存在、无效或当前角色不是该空间 owner/admin 时拒绝管理，不自动选择其他空间。

钉钉/OAuth2 的 `app_secret` 使用 `SECRET_KEY` 加密；Casdoor 使用独立加密配置版本。密钥轮换覆盖已有密文及认证状态，见[SECRET_KEY 轮换说明](./SECRET_KEY轮换runbook.md)。

### Casdoor SSO

SSO 配置、校验与本地登录账号关联保存于 `api/models/casdoor_extend.py`：

| 数据组 | 主要表 | 用途 |
|---|---|---|
| 集成配置 | `casdoor_integration_extend`、`casdoor_config_revision_extend` | 启用状态、生效/草稿版本、并发版本号、加密 Secret 与空间映射 |
| 身份来源 | `casdoor_namespace_extend`、`casdoor_identity_extend` | 保存 SSO 来源与已验证 subject 的本地账号关联 |
| 登录诊断 | `casdoor_validation_extend`、`casdoor_audit_extend` | 当前配置的检查摘要及不含凭据的登录证据 |
| 空间映射事实 | `casdoor_managed_membership_extend`、`casdoor_sync_intent_extend` | 登录时应用空间角色映射所需的内部关系与记录 |

配置版本不可直接改写。身份以 namespace + subject 摘要、namespace + account 双向唯一，防止同一身份来源的重复关联。配置读取不返回 Client Secret 明文，数据备份应覆盖加密 Secret 及对应密钥。

### 邀请事实

`api/models/invitation_authority_extend.py` 定义：

- `invitation_authority_lifecycle_extend`：账号/空间生命周期、代次与撤销状态。
- `invitation_authority_issuance_extend`：原始签发范围、Token/载荷摘要、消费状态与最终回执。

原始签发事实与成员权限分开保存。历史记录按设计留存，不能凭旧 Token 或旧 join 重新授予已撤销权限。表包含邮箱与精确载荷，备份、导出和截图需按敏感数据处理；回执不包含邮箱或明文 Token。

## Redis 与任务

数据库保存权威配置与事实，Redis 保存投影、短期认证状态及协调缓存。

| 缓存 | 维护方式 |
|---|---|
| `control_mail` | 邮箱名单投影；变更后全量重建，异常回退普通 sandbox |
| `webapp_auth_enabled_extend:{app_id}` | 登录开关投影；提交后失效，授权重查数据库 |
| `billing:payer_id:*` | 节点付款账号查询缓存 |
| Casdoor 认证/公钥缓存 | 短期认证事务、公钥与协调；不替代成员关系 |

`extend_high` 处理工作流 LLM 节点费用；`extend_low` 处理额度快照/重置。额度定时任务由 `ENABLE_EXTEND_QUOTA_RESET_TASKS` 控制。应分别核实数据库、队列消费与对象存储结果。

## 工作流归档

日志冷备用 S3 兼容存储保存 V2 bundle、Parquet、manifest 与目录分片，数据库保存 `workflow_run_archive_bundles` 等原生索引。归档表由上游链维护，不应在扩展链重复声明。

归档覆盖运行、应用日志、节点执行、卸载数据、暂停、暂停原因与触发日志；归档不删除源数据。恢复与删除按 bundle 校验对象大小、checksum、行数和源数据范围。对象、索引与源数据删除结果分别核验。

`batch_workflows_extend`、`batch_workflow_tasks_extend` 是旧 GVA 批量业务历史数据，未由扩展链创建，见[历史冷备说明](./批量工作流数据表冷备归档说明.md)。

## 保留结构与维护

`tenant_model_sync_extend`、`model_sync_config_extend` 保留旧数据，但当前服务没有有效调用链；表存在不代表跨空间同步可用。`forwarding_extend`、`forwarding_address_extend` 及费用记录也应按存量与真实入口维护，不能视为完整产品能力。

新增迁移应接在正确 revision 后，显式声明约束/索引并评估已有数据。租户读取沿完整空间/应用/资源范围检查；异步载荷 ID 从持久化事实重建权威上下文。数据回填、删除与降级需单独检查，存在 downgrade 函数不代表无损回滚。

升级完成只证明结构已部署；认证、计费、邀请、任务与存储需对应业务验证。历史记录见[文档索引](./README.md)，不能替代当前数据库状态。
