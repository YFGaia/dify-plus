## 1. 适用范围与执行说明

### 1.1 适用范围

- 本清单对应基线 tag **`fork-pre-merge-1.15.0`**。在该基线上执行应当 6 条链路全绿；后续在合并上游后的分支上重复执行时，任何一条链路不达预期即视为计费回归，需先修复再继续合并。
- 清单只覆盖 fork 自建计费体系（`account_money_extend` / `api_token_money_extend` 等扩展表），不涉及上游 `BillingService`（SaaS 云计费）。

### 1.2 执行前置条件（全局）

1. **三进程齐备**：api、worker、beat 必须同时运行——
   - api：Console / WebApp / Service API 的 HTTP 入口；
   - worker：必须监听 `extend_high,extend_low` 队列（链路 5 走 `extend_high`，链路 6 的任务落 `extend_low`）。docker 部署时对应 `docker/docker-compose.dify-plus.yaml` 中 `CELERY_QUEUES: ${CELERY_QUEUES:-extend_high,extend_low}` 的 worker 实例；源码运行时确认启动参数 `-Q` 包含这两个队列；
   - beat：链路 6 的 3 个定时任务由 beat 派发（`MODE=beat`，即 `celery -A app.celery beat`）。**beat 修改 schedule 后必须重启才生效**。
2. **数据库可查**：能对业务 PostgreSQL 执行 SQL（psql 或任意客户端），用于执行各链路的 SQL 断言。
3. **测试资产**：
   - 一个可登录 Console 的测试账号（记其邮箱，用于查 `account_id`）；
   - 一个已配置可用模型供应商的 chat 类应用（链路 1/2/3/4）；
   - 一个含 LLM 节点的 workflow 类应用（链路 5）；
   - 测试账号的 `account_money_extend` 剩余额度充足（`used_quota < total_quota`），否则请求会被余额拦截。
4. **通用查询**（后文 SQL 中的占位符按此获取，执行时替换为实际值）：

```sql
-- {account_id}：测试账号 ID
SELECT id FROM accounts WHERE email = '<测试账号邮箱>';

-- {app_id}：测试应用 ID（也可直接从 Console URL 中获取）
SELECT id, name, mode FROM apps WHERE name = '<测试应用名>';

-- {app_token_id}：Service API 密钥 ID（token 即 app-xxx 明文密钥）
SELECT id, token FROM api_tokens WHERE app_id = '{app_id}' AND type = 'app';
```

### 1.3 涉及的扩展表与字段（断言用，均已按模型定义核实）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `account_money_extend` | `account_id`、`total_quota`、`used_quota`、`updated_at` | 账号额度，`account_id` 唯一 |
| `api_token_money_extend` | `app_token_id`、`accumulated_quota`、`day_used_quota`、`month_used_quota`、`day_limit_quota`、`month_limit_quota`、`is_deleted` | 密钥额度与日/月限额（限额 `-1` 表示不限） |
| `api_token_message_joins_extend` | `app_token_id`、`record_id`、`app_mode` | 密钥↔消息/工作流运行 归因关联（`record_id` = `messages.id` 或 `workflow_runs.id`） |
| `end_user_account_joins_extend` | `end_user_id`、`account_id`、`app_id` | end_user↔账号 归因关联 |
| `account_money_monthly_stat_extend` | `account_id`、`total_quota`、`used_quota`、`stat_at` | 账号额度月快照（重置前留档） |
| `api_token_money_daily_stat_extend` | `app_token_id`、`accumulated_quota`、`day_used_quota`、`day_limit_quota`、`stat_at` | 密钥日额度快照 |

## 2. 六条回归链路

### 2.1 链路 1：Console 调试运行扣费（Blinker `message_was_created` 链路）

链路说明：Console 调试（预览）发消息 → 消息落库触发 Blinker 信号 `message_was_created` → `api/events/event_handlers/update_account_money_when_messaeg_created_extend.py` 的 `handle` 同步扣费。该链路在 api 进程内同步执行，不经 Celery。

【前置条件】

- api 进程运行中；测试账号可登录 Console；chat 类应用已配好模型且可正常对话。
- 记录扣费前基线：

```sql
SELECT used_quota, updated_at FROM account_money_extend WHERE account_id = '{account_id}';
```

【操作步骤】

1. 用测试账号登录 Console，打开 chat 应用的编排页。
2. 在右侧「调试与预览」面板发送一条会实际调用 LLM 的消息（如“用一句话介绍你自己”），等待回复完成。
3. 查询本次消息的费用：

```sql
SELECT id, total_price, currency, from_account_id
FROM messages
WHERE app_id = '{app_id}' AND from_account_id = '{account_id}'
ORDER BY created_at DESC LIMIT 1;
```

【预期断言】

1. 上面查出的最新消息 `from_account_id = {account_id}`，`total_price > 0`。
2. `account_money_extend.used_quota` 增量等于该消息折算后的费用（USD 消息即等于 `total_price`，误差在 Numeric(16,7) 精度内）：

```sql
SELECT used_quota FROM account_money_extend WHERE account_id = '{account_id}';
-- 断言：本值 - 基线值 ≈ messages.total_price（currency='USD' 时相等；否则为 total_price / RMB_TO_USD_RATE）
```

3. 若测试账号此前没有 `account_money_extend` 记录，断言改为：新插入了一行，`used_quota` = 本次费用、`total_quota` = 配置默认值（`ACCOUNT_TOTAL_QUOTA`，默认 15）。

### 2.2 链路 2：Explore 运行扣费

链路说明：Explore（应用中心/工作区已安装应用）中以 Console 登录身份运行应用，消息 `from_account_id` 直接记录登录账号，扣费同样走链路 1 的 Blinker handler，验证 `InvokeFrom.EXPLORE` 入口未回退。

【前置条件】

- 链路 1 已通过（同一 handler，链路 2 主要验证入口）。
- 测试 chat 应用已发布并添加到工作区（Explore/应用中心可见、可打开对话）。
- 记录扣费前基线（同链路 1 的基线 SQL）。

【操作步骤】

1. 用测试账号登录 Console，进入「探索/应用中心」，打开该已安装应用。
2. 发送一条会实际调用 LLM 的消息，等待回复完成。

【预期断言】

1. 最新消息归属正确（注意 Explore 运行时 `from_account_id` 仍为登录账号）：

```sql
SELECT id, total_price, currency, from_account_id, invoke_from
FROM messages
WHERE app_id = '{app_id}'
ORDER BY created_at DESC LIMIT 1;
-- 断言：from_account_id = '{account_id}' 且 total_price > 0
```

2. `account_money_extend.used_quota` 相对基线增加该消息折算费用（断言 SQL 同链路 1）。

### 2.3 链路 3：WebApp 登录 + 扣费（含 `end_user_account_joins_extend` 归因）

链路说明：fork 强制 WebApp 必须携带 Console 登录态（`is_end_login`，见 `api/controllers/web/completion.py`）。登录后请求会把 Console 账号 ID 经 `args["account_id"]` → `extras["account_id"]` 写入消息的 `from_account_id`，Blinker handler 据此直扣账号额度；未直扣路径（消息只有 `from_end_user_id`）则由 handler 回查 `end_user_account_joins_extend` 归因到账号。

【前置条件】

- 测试 chat 应用已发布 WebApp（拿到 `/chat/<code>` 公开访问链接）。
- 浏览器 A：已登录 Console 的会话；浏览器 B（或无痕窗口）：无 Console 登录态。
- 记录扣费前基线（同链路 1），并记录归因表基线：

```sql
SELECT COUNT(*) FROM end_user_account_joins_extend WHERE app_id = '{app_id}';
```

【操作步骤】

1. **未登录拦截**：在浏览器 B 打开 WebApp 链接并尝试发消息。
2. **登录后扣费**：在浏览器 A（带 Console 登录态）打开同一 WebApp 链接，发送一条会实际调用 LLM 的消息，等待回复完成。

【预期断言】

1. 步骤 1 的发送请求被拒：HTTP 401，响应 body 含 `"code": "unauthorized"`（`WebAuthRequiredErrorExtend`），且 `account_money_extend.used_quota` 无变化。
2. 步骤 2 成功后，最新消息已归因到 Console 账号：

```sql
SELECT id, total_price, currency, from_account_id, from_end_user_id
FROM messages
WHERE app_id = '{app_id}'
ORDER BY created_at DESC LIMIT 1;
-- 断言：from_account_id = '{account_id}'（chat/agent_chat/completion 应用登录直扣路径）
```

3. `account_money_extend.used_quota` 相对基线增加该消息折算费用（断言 SQL 同链路 1）。
4. 归因关联可用（end_user 绑定与关联表二者至少其一成立，保证 handler 的回查路径有据可依）：

```sql
-- 4a. end_user 已绑定 Console 账号
SELECT id, external_user_id FROM end_users
WHERE app_id = '{app_id}' ORDER BY updated_at DESC LIMIT 1;
-- 断言：external_user_id = '{account_id}'

-- 4b. 归因关联表存在该 end_user 到账号的映射（Service API 路径写入；WebApp 直扣路径可能不落此表，见下方注意）
SELECT end_user_id, account_id, app_id FROM end_user_account_joins_extend
WHERE account_id = '{account_id}' AND app_id = '{app_id}';
```

> 注意：当前代码中 `end_user_account_joins_extend` 的写入点在 `api/controllers/service_api/wraps.py` 的 `create_or_update_end_user_account_join_extend`（Service API 带 user 参数的调用路径）。WebApp 登录路径对 chat/agent_chat/completion 应用走 `from_account_id` 直扣，可以不依赖此表；若步骤 2 使用的是 chatflow（advanced-chat）应用且消息只有 `from_end_user_id`，则断言 4b 必须成立，否则扣费会落错账户。执行时以断言 3（额度确实扣到 Console 账号）为最终判定。

### 2.4 链路 4：Service API 密钥日/月限额拦截

链路说明：Service API 请求经 `api/controllers/service_api/wraps.py` 的 `validate_app_token` 前置校验（账号总额度 → 密钥日限额 → 密钥月限额，超限分别抛 403）；放行的请求在 app_generator 写入 `api_token_message_joins_extend` 归因记录，消息落库后由 Blinker handler 同时累计 `api_token_money_extend` 的 `accumulated_quota` / `day_used_quota` / `month_used_quota`。**日限额与月限额需分别断言。**

【前置条件】

- 测试 chat 应用已创建 Service API 密钥（Console → 应用 → API 访问，创建时可设 `day_limit_quota` / `month_limit_quota`，默认 `-1` 不限）。
- 记录密钥额度基线：

```sql
SELECT app_token_id, accumulated_quota, day_used_quota, month_used_quota,
       day_limit_quota, month_limit_quota
FROM api_token_money_extend WHERE app_token_id = '{app_token_id}';
```

【操作步骤】

1. **正常累计**：用密钥调用一次 Service API（blocking 便于断言）：

```bash
curl -sS -X POST '<API_BASE>/v1/chat-messages' \
  -H 'Authorization: Bearer <app-xxx密钥明文>' \
  -H 'Content-Type: application/json' \
  -d '{"inputs":{},"query":"用一句话介绍你自己","response_mode":"blocking","user":"billing-regression-user"}'
```

2. **日限额拦截**：把该密钥 `day_limit_quota` 调成小于当前 `day_used_quota` 的正数（可经 Console 密钥编辑接口，或临时用 SQL：`UPDATE api_token_money_extend SET day_limit_quota = 0.0000001 WHERE app_token_id = '{app_token_id}';`），再次执行步骤 1 的 curl。
3. **月限额拦截**：恢复 `day_limit_quota = -1`，把 `month_limit_quota` 调成小于当前 `month_used_quota` 的正数，再次执行步骤 1 的 curl。
4. 收尾：把两个限额恢复为 `-1`（或原值）。

【预期断言】

1. 步骤 1 返回 200，且归因记录已写入：

```sql
SELECT app_token_id, record_id, app_mode FROM api_token_message_joins_extend
WHERE app_token_id = '{app_token_id}' ORDER BY created_at DESC LIMIT 1;
-- 断言：record_id = 本次响应中的 message_id
```

2. 步骤 1 后密钥三个累计字段同步增加同一费用增量：

```sql
SELECT accumulated_quota, day_used_quota, month_used_quota
FROM api_token_money_extend WHERE app_token_id = '{app_token_id}';
-- 断言：三者相对基线增量一致且 > 0；同时 account_money_extend（工作区 owner 账号）的 used_quota 亦增加
```

3. **日限额断言**：步骤 2 的 curl 返回 HTTP 403，响应 body 含
   `The daily call limit for this key has been reached, the call failed!`（`ApiTokenDayNoMoneyErrorExtend`），且 `api_token_money_extend` 三个累计字段无变化（请求被前置拦截，未产生消息）。
4. **月限额断言**：步骤 3 的 curl 返回 HTTP 403，响应 body 含
   `The monthly call limit for this key has been reached, the call failed!`（`ApiTokenMonthNoMoneyErrorExtend`），且累计字段无变化。

### 2.5 链路 5：workflow LLM 节点扣费（Celery `extend_high` 队列链路）

链路说明：workflow/chatflow 的节点执行成功后，`api/core/app/workflow/layers/persistence.py` 的 `_handle_node_succeeded` 派发 Celery 任务 `update_account_money_when_workflow_node_execution_created_extend.delay(...)`（`api/tasks/extend/`，队列 `extend_high`，`max_retries=3`）。任务只对 `node_type = 'llm'` 且 `total_price > 0` 的节点扣费；`created_by_role = 'end_user'` 时经 Redis 缓存 + `end_user_account_joins_extend` 解析付费人。

【前置条件】

- worker 监听 `extend_high` 队列（`celery -A app.celery inspect active_queues` 中可见 `extend_high`）。
- 含 LLM 节点的 workflow 应用可正常运行。
- 记录扣费前基线（同链路 1 的基线 SQL）。

【操作步骤】

1. 用测试账号在 Console 运行该 workflow（编排页「运行」，填入必要输入），等待运行成功。
2. 观察 worker 日志，应出现该任务的执行痕迹：`工作流节点ID： <uuid>` 与 `扣除费用： <金额>`、`更新账号额度，账号ID： {account_id}`。
3. 因扣费是异步任务，等待数秒（异常重试间隔为 60 秒）后再执行断言。

【预期断言】

1. worker 日志确认任务在 `extend_high` 队列被消费且无报错（无 `数据库异常，60秒后进行重试` 字样）。
2. `account_money_extend.used_quota` 相对基线增加 LLM 节点费用之和（多 LLM 节点时为各节点 `outputs.usage.total_price` 折算后之和）：

```sql
SELECT used_quota FROM account_money_extend WHERE account_id = '{account_id}';
-- 断言：本值 - 基线值 ≈ Σ(LLM 节点 usage.total_price 折算值) > 0
```

3. 若该次运行经 Service API 触发（extras 带 `app_token_id`），则 `api_token_message_joins_extend` 中存在 `record_id = workflow_run_id` 的记录，且 `api_token_money_extend` 三个累计字段同额增加：

```sql
SELECT app_token_id, record_id, app_mode FROM api_token_message_joins_extend
WHERE record_id = '<workflow_run_id>';
```

> 注意：chatflow（advanced-chat）应用会同时命中链路 1（消息级）与本链路（节点级）两个扣费点，历史行为如此；回归本链路请使用**纯 workflow 应用**，避免增量断言混淆。

### 2.6 链路 6：月初额度重置（3 个 Celery beat 任务）

链路说明：`api/extensions/ext_celery.py` 「二开部分」注册 3 个 beat 任务（任务本体在 `api/schedule/`，队列 `extend_low`）：

| 任务 | crontab | 行为 |
|---|---|---|
| `schedule.update_account_used_quota_extend.update_account_used_quota_extend` | 每月 1 号 00:00 | 全表快照 `account_money_extend` → `account_money_monthly_stat_extend`，然后 `used_quota` 清零 |
| `schedule.update_api_token_daily_used_quota_task_extend.update_api_token_daily_used_quota_task_extend` | 每天 00:00 | 快照 → `api_token_money_daily_stat_extend`，然后 `day_used_quota` 清零 |
| `schedule.update_api_token_monthly_used_quota_task_extend.update_api_token_monthly_used_quota_task_extend` | 每月 1 号 00:00 | 快照 → `api_token_money_monthly_stat_extend`，然后 `month_used_quota` 清零 |

【前置条件】

- beat 与 worker（监听 `extend_low`）均在运行；beat 为挂点恢复后重启过的进程。
- 库中存在非零数据：至少一行 `account_money_extend.used_quota > 0`、一行 `api_token_money_extend.day_used_quota > 0` 且 `month_used_quota > 0`（可先跑链路 1/4 制造数据）。
- 记录重置前基线：

```sql
-- 基线 A：待重置的额度值
SELECT account_id, used_quota FROM account_money_extend WHERE used_quota > 0;
SELECT app_token_id, day_used_quota, month_used_quota FROM api_token_money_extend
WHERE day_used_quota > 0 OR month_used_quota > 0;

-- 基线 B：快照表当前行数
SELECT COUNT(*) FROM account_money_monthly_stat_extend;
SELECT COUNT(*) FROM api_token_money_daily_stat_extend;
SELECT COUNT(*) FROM api_token_money_monthly_stat_extend;
```

【操作步骤】——两种执行方式任选其一（合并后的首轮回归建议至少手动触发一次全部 3 个任务）

**方式一：自然触发（等 crontab）**

1. 等待自然窗口：日任务等次日 00:00；两个月任务等下月 1 号 00:00。
2. 窗口过后检查 beat 日志出现任务派发记录、worker 日志出现
