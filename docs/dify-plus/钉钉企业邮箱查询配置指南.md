# 钉钉企业邮箱查询配置指南

入口：系统管理 → 系统集成 → 钉钉 → 企业邮箱查询。

该功能用于钉钉登录时，根据钉钉用户 ID 从企业通讯录或员工接口查询邮箱。系统按该邮箱匹配已有 Dify 账号，未找到账号时自动注册。它不负责发送验证码、邀请或重置密码邮件；邮件发送仍由部署的 MAIL_TYPE 及对应 SMTP、Resend、SendGrid 配置控制。

## 常见配置

以企业接口 `GET https://directory.example.com/users/email?userId=员工钉钉ID` 返回下面结构为例：

```json
{"data": [{"userName": "employee@example.com"}]}
```

1. 打开企业邮箱查询开关。
2. API 地址填 `https://directory.example.com/users/email`，请求方式选 GET。
3. 用户 ID 参数名填 `userId`。无需在地址中手动拼接这个参数，系统会填入当前登录用户的钉钉 ID。
4. 返回邮箱字段填 `data[0].userName`。返回 `{"data":{"email":"employee@example.com"}}` 时改填 `data.email`；顶层 email 字段填 `email`。
5. 如果接口要求 `Authorization: Bearer ...`，选择 Bearer 并输入 Token；HTTP Basic 选择 Basic 并填写用户名、密码；其他鉴权可在高级请求头 JSON 中配置。
6. 输入一个真实的钉钉用户 ID，点击测试邮箱查询，确认展示的是该员工的正确邮箱。
7. 点击钉钉配置的保存按钮。测试使用当前草稿，不会保存配置，也不会创建账号。

接口必须返回 HTTP 200 和可提取的邮箱字符串。API 地址应能从 Dify 后端访问，并符合部署的 SSRF 代理策略；测试失败时检查地址、鉴权、用户 ID 和返回字段路径。

## POST 及高级配置

请求方式为 POST 时，默认将用户 ID 作为 JSON 字段发送。高级请求体配置沿用既有结构：

```json
{"raw": "{\"tenant\":\"example\"}"}
```

上述配置和默认参数名会发送：

```json
{"tenant":"example","userId":"当前钉钉用户ID"}
```

选择表单请求体时分别使用 `form_data` 或 `urlencoded`：

```json
{"urlencoded": [{"key": "tenant", "value": "example"}]}
```

请求头使用 JSON 对象，如 `{"X-Directory":"enterprise"}`。用户 ID 参数始终由系统填入，覆盖请求体中同名字段。原有 PUT/DELETE、Basic 鉴权、请求头、表单请求体及其他钉钉扩展字段继续保留。

## 登录行为与生效范围

启用并保存后，钉钉登录和第三方钉钉登录使用此配置。读取邮箱的优先级为：企业接口 → 钉钉用户资料邮箱 → 姓名拼音或用户 ID 与 EMAIL_DOMAIN 组合生成的邮箱。

企业查询失败或关闭开关时，仍使用后续邮箱来源。生成的邮箱不保证是真实可收信地址。更改企业接口返回邮箱可能改变匹配到的 Dify 账号，系统不会直接更新已有账号邮箱。正式启用前应确认企业接口返回邮箱与现有 Dify 账号一致。

配置保存在原有钉钉 `config.email_api`，无需数据库迁移。普通邮箱登录、OAuth2、Casdoor 登录不使用这项配置。
