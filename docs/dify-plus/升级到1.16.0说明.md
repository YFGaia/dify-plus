# 升级到 1.16.0 说明（自 1.15.0）

本文面向从 Dify-Plus `1.15.0`（基线 tag `fork-merged-1.15.0`）升级到 `1.16.0`
（基线 tag `fork-merged-1.16.0`）的部署方。上游跨度为 Dify 1.15.0 → 1.16.0（一次合并完成，
455 个上游提交）。与 1.15.0 那轮不同，本轮**无破坏性架构变更**：没有服务下线、没有 fork 表结构
变化、没有新增一次性回填命令，数据库迁移就是标准两段命令。

> 通用的上游升级流程与回归范围见[上游升级与回归检查清单](./上游升级与回归检查清单.md)；
> 本文是一次性的版本专项说明，两者配合使用。
> 实际演练记录（全新库迁移双链 + api 冒烟，含踩坑）见
> [1.16.0 升级本地容器验证记录](./1.16.0升级本地容器验证记录.md)；
> 发布前的 UI 人工回归项见[人工回归清单-1.16.0](./人工回归清单-1.16.0.md)。
> 从 1.12.1（或更早、仍含 GVA 管理后台的版本）升级，先读
> [升级到 1.15.0 说明](./升级到1.15.0说明.md)完成到 1.15.0，再按本文继续。

## 1. 重大变更一览

### 1.1 上游行为变化（影响运维与集成，重点）

- **console 登录 `password` 必须 Base64 编码**：1.16.0 上游给 `POST /console/api/login`
  加了 `@decrypt_password_field`，明文直传返回 401 "Invalid encrypted data"。
  Console 前端已适配；**受影响的是直调登录接口的 fork 脚本/巡检/自动化工具**。
- **console 会话改 Cookie + CSRF**：登录态由 HttpOnly Cookie（`access_token` /
  `refresh_token`）+ 非 HttpOnly `csrf_token` Cookie 承载，且 `login_required` 内嵌 CSRF
  校验——所有 console API 调用须同时带 Cookie 和 `X-CSRF-Token` 头（值取 `csrf_token`
  cookie），仅带 Cookie 会 401。同样只影响直调 API 的脚本/工具，浏览器端无感。
- **Agent v2 配套服务**：上游新增 `agent_backend`、`local_sandbox` 两个服务，fork compose
  已同步（见 §4）。fork 保持 **Agent v2 默认关闭**（`ENABLE_AGENT_V2:-false`，上游默认已
  翻转为 true）；不启用则这两个服务不参与业务链路。

### 1.2 fork 侧变化

- **邀请成员弹窗**：fork 自制的多邮箱输入组件（react-multi-email-extend）被上游原生
  `EmailRecipientsField` 吸收后删除。**功能损失**：「输入裸用户名自动补默认邮箱域
  （`NEXT_PUBLIC_DEFAULT_DOMAIN`）」能力随之退役，邀请时需输入完整邮箱。
- **记忆上下文 `retention_number` 修复**：1.15.0 时该字段挂在已死的响应字典上，web 配置页
  实际读不到；本轮迁移到新响应模型后顺带修复，配置页可正常回显。
- 其余均为内部结构适配（挂点重挂、契约层迁移、i18n 体系跟随上游），对部署方无感；
  明细见[与上游差异总表 §4.7](./与上游差异总表.md)。

## 2. 升级前准备（强制）

1. `pg_dump` 整库快照 + 生产 `.env` 备份。上游 1.16.0 新增 5 个迁移（2 张新表 + 3 处加列），
   跨版本 `flask db downgrade` 未经验证，快照是唯一可靠的 DB 回滚手段。
2. 停止全部服务：api / worker / worker_beat / web（及 `api_websocket`，如启用了 collaboration）。
3. 更新代码 / 镜像到 `1.16.0`（镜像 tag 变化见 §4）。

## 3. 数据库迁移序列（两段命令即可）

在 api 容器（或源码环境）内依次执行：

```bash
# 1) 上游迁移链（1.15.0 → 1.16.0 新增 5 个迁移，终点 7a1c2d9e4b60）
flask db upgrade

# 2) fork 扩展链（本轮无新增迁移，head 仍为 018_drop_recommended_cats；
#    执行以校验双链状态，幂等无害）
flask extend_db upgrade
```

**无需任何一次性命令**（已在全新库实测 + 代码考证，见验证记录 §4）：

| 命令 | 结论 |
| --- | --- |
| `flask rbac-migrate-dataset-permissions` / `rbac-migrate-member-roles` | 不执行。RBAC 由企业版配置 `RBAC_ENABLED` 门禁（fork 自托管默认不启用）；仅显式开启企业 RBAC 时才需要，且默认 dry-run |
| `flask backfill-workflow-run-archive-bundles` | 不执行。workflow-run 归档是 1.16.0 新功能，存量环境无可回填之物；未配 `ARCHIVE_STORAGE_ARCHIVE_BUCKET` 时直接报错属预期 |
| `flask backfill-plugin-auto-upgrade` | 1.15.0 已升级过的环境无需重跑（幂等，重复执行无害）；从 1.14.x 及更早**直跳** 1.16.0 的环境仍按 1.15.0 说明保留为第三步 |

迁移抽验：

```sql
SELECT version_num FROM alembic_version;          -- 期望 7a1c2d9e4b60
SELECT version_num FROM alembic_version_extend;   -- 期望 018_drop_recommended_cats
```

## 4. 环境变量与部署拓扑对齐

以 1.16.0 的 [`docker/.env.example`](../../docker/.env.example) 为准逐项比对生产 `.env`，重点：

| 变量 | 说明 |
| --- | --- |
| `DIFY_AGENT_SERVER_SECRET_KEY` | **fork 不内置默认值**（上游样例是公开弱密钥，fork 改为空占位）。不启用 Agent v2 可留空（agent_backend 不可用但不影响其他服务）；启用前必须生成强随机值 |
| `DIFY_AGENT_SHELLCTL_AUTH_TOKEN` | 同上，建议与上一项一并配置 |
| `NEXT_PUBLIC_ENABLE_AGENT_V2` | 上游把 `ENABLE_AGENT_V2` 改名并默认 true；fork compose 兼容旧名且**默认 false**（`NEXT_PUBLIC_ENABLE_AGENT_V2:-${ENABLE_AGENT_V2:-false}`），存量 `.env` 的旧配置继续生效 |
| `API_WEBSOCKET_WORKER_AMOUNT` | 新增：api_websocket 服务的 worker 数（默认 1） |
| `REDIS_KEEPALIVE*` 四件套 | 新增：Redis keepalive，默认跟上游 |
| `WORKFLOW_GENERATION_TIMEOUT_MS` | 新增：web 侧工作流生成超时（默认 180000） |
| SSRF 白名单两项 | 1.15.0 引入，本轮无变化；确认未丢失 |

拓扑与镜像变更（fork compose `docker-compose.dify-plus.yaml` 已同步）：

- **新增服务**：`agent_backend`（`langgenius/dify-agent-backend:1.16.0`）、
  `local_sandbox`（`langgenius/dify-agent-local-sandbox:1.16.0`）。这两个镜像暂直连官方源，
  内网环境可自行镜像后改 compose。
- **镜像 tag**：`dify-plus-api` / `dify-plus-web` → `1.16.0`（需 CI 构建并推送私有仓）；
  `dify-plugin-daemon` `0.5.2-local` → `0.6.3-local`；`dify-sandbox` `0.2.12` → `0.2.15`
  （确认私有仓已镜像对应 tag）。

## 5. 启动与回归

```bash
cd docker
docker compose -f docker-compose.dify-plus.yaml up -d
```

回归按[人工回归清单-1.16.0](./人工回归清单-1.16.0.md)执行（三方登录、应用中心、
计费整栈、系统管理三页、webapp-signin 等）；计费链路细化步骤见
[计费回归基线清单](./计费回归基线清单.md)。

## 6. 回滚路径

- 代码：回退到 tag `fork-merged-1.15.0`（合并前安全点为 `fork-pre-merge-1.16.0`）。
- 数据库：用第 2 步 pg_dump 快照整库恢复（上游新迁移的 downgrade 未经验证，不要依赖）。
- 本轮 fork 扩展链无变化，扩展表数据不受升级影响。

## 7. 运维注意事项（本轮实测 + 沿袭）

- **直调 console API 的下游先行适配**：password Base64 + Cookie/CSRF（§1.1）是本轮最大的
  集成面变化，升级窗口前先排查监控脚本、巡检、e2e、对接工具。
- `docker/docker-compose.middleware.yaml` 引用的 `./middleware.env` 在仓库中不存在，
  单独起中间件验证时需先建该文件（或用等价最小 compose，见容器验证记录 §1）。
- 代理环境下 docker.io 拉镜像可能长时间挂起，优先使用私有仓/腾讯云镜像缓存。
- 沿袭 1.15.0 说明：替换 api / web 容器后建议 `docker compose restart nginx`（上游 DNS
  解析陈旧会 502）；web 镜像构建内存要求高（Docker VM ≥10GB）；升级窗口内避免反复重启
  worker（额度重置任务可能被积压消息补跑，任务幂等但会出现计划外清零）。
