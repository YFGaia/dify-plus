## 依赖与并行关系

```
P0 基线止血 ──────────► P2 合并1.14.2 ──► P3 合并1.15.0 ──┬─► P4 计费加固
                                                          └─► P6 前台规范化
P1 批量工作流决策门 ──（决策+后端部分可提前）──► P5 admin废弃
```

**并行批次建议**：

| 批次 | 可并行的提案 | 说明 |
|---|---|---|
| 批次 1 | **P0 + P1（决策门部分）** | P0 是全局阻塞项；P1 的使用量 SQL 验证与业务确认不碰代码，可同时进行 |
| 批次 2 | **P2（独占）**，P1 方案 B 的后端设计/迁移脚本可并行准备 | git merge 状态不可并行编辑，P2 期间避免其他提案改 api/web 代码 |
| 批次 3 | **P3（独占）** | 同上；P1 方案 B 的前端改造必须等 P3 完成（text-generation/index.tsx 被上游大改） |
| 批次 4 | **P4 + P5 + P6 三线并行** | 代码交叉面小：P4 主攻 api 计费链路，P5 主攻 admin/部署/api 清理项，P6 主攻 web 前台。唯一交叉点：P5 的 control_mail 管理页挂在 system-manage-extend 下，若 P6 同时重构该目录，control_mail 新页面应直接按 P6 规范（contract-first）实现 |
| 收尾 | P5 的 SECRET_KEY 轮换与 DROP 表 | 不可逆操作，单独安排窗口、人工确认 |

**提案内部并发**：每个提案的 `tasks.md` 均包含「并发执行策略」小节，标注了哪些任务可交 sub-agent 并行（如 P3 的 main-nav 四挂载点重做/headlessui 清退/SSRF 对齐、P4 的六个独立加固项、P6 的按页面并行改造），哪些必须主 agent 顺序执行（merge 冲突解决、共享文件修改、不可逆操作）。
