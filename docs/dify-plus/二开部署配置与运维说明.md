# Dify-Plus 部署配置与运维说明

Dify-Plus 的标准部署由 Dify API、Web、后台任务及其基础设施组成，系统管理直接使用 Console 原生页面和 API。项目已去除 GVA 独立后台，不需要额外管理端服务或共享管理密钥。本文描述当前仓库部署方式；源码基于 Dify 1.17.1，实际运行版本以部署镜像及配置为准。

## 部署入口与服务

使用 [`docker/docker-compose.dify-plus.yaml`](../../docker/docker-compose.dify-plus.yaml)。官方 `docker-compose.yaml` 是上游部署入口，不能直接替代包含扩展任务、扩展沙箱及双迁移链的 fork 编排。

| 服务 | 职责 |
| --- | --- |
| `nginx`、`web`、`api` | 统一入口、Console / WebApp 页面、业务 API |
| `api_websocket` | 工作流 Socket.IO 服务，由 `collaboration` profile 启用 |
| `worker` | 知识库、工作流、邮件、插件等任务；默认包含 `workflow_based_app_execution` 队列 |
| `worker-gaia` | `extend_high` / `extend_low` 扩展任务，包括工作流计费 |
| `worker-dataset` | `dataset` / `priority_dataset` 文档索引队列 |
| `worker_beat` | 周期调度，包括额度重置和工作流调度 |
| `init_permissions`、`init_secret_key` | 共享存储权限和持久化密钥初始化 |
| `migration` | 单次执行上游和扩展迁移，仅在 `migration` profile 中启用 |
| `db_postgres` / `db_mysql`、`redis`、向量库 | 业务数据、缓存 / 队列和向量索引 |
| `plugin_daemon`、`sandbox`、`ssrf_proxy` | 插件、普通代码执行和出站代理 |
| `sandbox-full` | 授权完整代码执行；仅在 `full-sandbox` profile 中启用，需独立核验供应镜像 |
| `agent_backend`、`local_sandbox`、`agent_ssrf_proxy` | Agent v2 后端和沙箱环境 |

API、WebSocket、各 worker、调度、初始化密钥及迁移服务必须使用同一发布的 fork API 镜像。Compose 配置的容器版本为 `1.17.1-plus.2`，四组件名称与变量如下；默认值不表示稳定标签已经构建成功。部署前核对[容器发布与验收状态](./容器镜像发布与多架构部署.md)，确认 GHCR 镜像可拉取、两架构 manifest 及源码 revision 一致，并保存不可变 digest。

| 镜像变量 | 默认镜像 |
| --- | --- |
| `DIFY_PLUS_API_IMAGE` | `ghcr.io/yfgaia/dify-plus-api:1.17.1-plus.2` |
| `DIFY_PLUS_WEB_IMAGE` | `ghcr.io/yfgaia/dify-plus-web:1.17.1-plus.2` |
| `DIFY_PLUS_AGENT_IMAGE` | `ghcr.io/yfgaia/dify-plus-agent-backend:1.17.1-plus.2` |
| `DIFY_PLUS_LOCAL_SANDBOX_IMAGE` | `ghcr.io/yfgaia/dify-plus-agent-local-sandbox:1.17.1-plus.2` |

## 配置分层

| 文件 | 用途 |
| --- | --- |
| `docker/.env.example` → `docker/.env` | Compose 必需项和实际部署覆盖值 |
| `docker/envs/**/*.env.example` | 可选配置及提供商参数参考 |
| `docker/docker-compose.dify-plus.yaml` | fork 服务、显式环境映射、网络和挂载 |
| `api/.env.example`、`web/.env.example` | 非容器开发环境参考 |
| 自定义 Compose override | 镜像固定、未映射配置、额外挂载和环境差异 |

**fork Compose 使用显式 `environment` 映射，不读取服务级 `env_file`。** 将可选参数写入 `docker/.env` 前，先检查它是否已映射；未映射项必须通过服务的 `environment` override 注入。仅复制 `docker/envs` 示例不会自动配置 fork 部署。上游 Compose 的服务 env 文件机制与此不同。

| 参数 | 配置要点 |
| --- | --- |
| `COMPOSE_PROFILES` | 默认启用向量库、数据库及 `collaboration`；与 `VECTOR_STORE` / `DB_TYPE` 一致；完整沙箱另加 `full-sandbox` |
| `DIFY_PLUS_*_IMAGE` | 四组件镜像可指定已验证版本或 `名称@sha256:...`；API 消费者共用 `DIFY_PLUS_API_IMAGE` |
| `DIFY_PLUS_FULL_SANDBOX_IMAGE`、`FULL_CODE_EXECUTION_ENDPOINT` | 可选完整沙箱的供应镜像及调用地址；先核验架构并启用 profile，再配置 owner 邮箱授权 |
| `DIFY_AGENT_SERVER_SECRET_KEY` | 启动前必填独立强随机值，即使 Agent v2 功能关闭；必须为无 `=` 填充的 base64url 文本且解码为 32 字节。可用 `python -c 'import secrets; print(secrets.token_urlsafe(32))'` 生成；用于 Agent Stub JWE 密钥派生 |
| `SECRET_KEY` | 显式值须由所有 API 消费者共享；留空时初始化任务生成并持久化到存储 `.dify_secret_key` |
| `DB_*`、`REDIS_*`、`CELERY_BROKER_URL` | 数据库、缓存、队列；修改 Redis 密码时同步 broker URL |
| `CONSOLE_API_URL`、`CONSOLE_WEB_URL`、`APP_API_URL`、`APP_WEB_URL`、`SERVICE_API_URL` | 控制台、WebApp、Service API 的实际访问地址 |
| `FILES_URL`、`INTERNAL_FILES_URL` | 对外文件和容器内部文件地址；插件及 Agent 需能访问内部地址 |
| `NEXT_PUBLIC_SOCKET_URL` | 浏览器可访问的 WebSocket 地址；HTTPS 使用对应 `wss://` 地址并包含实际端口 |
| `NGINX_SOCKET_IO_UPSTREAM` | 默认 `api_websocket:5001`，与协作服务一致 |
| `STORAGE_TYPE`、`OPENDAL_SCHEME`、存储提供商参数 | 文件和持久化密钥存储；所有消费者配置一致 |
| `VECTOR_STORE` 及对应参数 | 与启用的 profile、网络和实际向量库对应 |
| `SANDBOX_API_KEY`、`PLUGIN_DAEMON_KEY`、`PLUGIN_DIFY_INNER_API_KEY` | 使用部署自有凭据，相关服务保持一致 |
| `DIFY_AGENT_API_TOKEN`、`DIFY_AGENT_LOCAL_SANDBOX_AUTH_TOKEN` | Agent 控制面和沙箱认证；API 与 Agent 后端匹配 |
| `EMAIL_DOMAIN`、`RMB_TO_USD_RATE` | 邮箱域和金额换算，以部署值为准 |
| `ACCOUNT_TOTAL_QUOTA`、`DEFAULT_NUMBER_CONTEXT`、`ENABLE_EXTEND_QUOTA_RESET_TASKS` | 初始余额、默认记忆窗口、额度重置；当前 fork Compose 未映射，定制时通过 override 注入 |

不要将实际密码、Secret、私有登录地址或原始配置输出提交到文档。Casdoor Client Secret 由授权管理员在配置页输入，保存在加密数据库字段中。

## 全新安装

以下从仓库根开始，面向默认 PostgreSQL / Weaviate 的新环境。Docker Compose 需支持长格式依赖条件；先确认四组件稳定标签已通过发布验证。已有环境升级见下一节，不能以新装命令直接启动旧 Weaviate 数据卷。

```bash
cd docker
cp .env.example .env
# 编辑 .env：至少填写 DIFY_AGENT_SERVER_SECRET_KEY，配置部署凭据和入口地址。
docker compose -f docker-compose.dify-plus.yaml config --quiet
docker compose -f docker-compose.dify-plus.yaml pull
docker compose -f docker-compose.dify-plus.yaml up -d db_postgres redis
docker compose -f docker-compose.dify-plus.yaml up --no-deps --abort-on-container-exit --exit-code-from init_permissions init_permissions
docker compose -f docker-compose.dify-plus.yaml up --no-deps --abort-on-container-exit --exit-code-from init_secret_key init_secret_key
docker compose -f docker-compose.dify-plus.yaml --profile migration up --no-deps --abort-on-container-exit --exit-code-from migration migration
```

每一步成功后再执行下一步，等待数据库健康。初始化任务与迁移串行执行；`--no-deps` 不会自动完成依赖。迁移依次运行 `flask db upgrade`、`flask extend_db upgrade`，并输出两条链的当前 revision。核对双链版本、表结构和必要数据后启动业务：

```bash
docker compose -f docker-compose.dify-plus.yaml up -d
docker compose -f docker-compose.dify-plus.yaml ps
```

默认本机入口为 `http://localhost/install`，完成初始账号及空间创建。自定义端口或域名时访问对应 `/install`。只有当前处于初始化空间且真实角色为 `owner` / `admin` 的账号能使用系统管理。

验证登录、应用发布 / 应用中心、真实模型调用、余额与密钥额度、知识库索引 / 检索及工作流编辑。工作流还需检查实际 Socket.IO `101` 握手和节点点击；容器 healthy 或 REST 200 不能证明协作正常。

## 已有环境升级与恢复

升级需要目标部署的一致恢复点，操作包见[升级与回归 runbook](../../openspec/changes/merge-upstream-1-17-1/runbook.md)。历史源码或本地验收记录不代替本次部署验收。

1. 记录实际 Compose 全部叠加文件、环境、API / Web / 插件 / Agent 镜像 digest、存储及数据库版本，保留旧配置。
2. 关闭入口，停止 API、WebSocket、所有 worker、beat、Agent 和其他写入者；建立数据库、向量库、Redis、文件 / 插件存储的配套备份及队列处置记录。
3. 确认同一数据库只有一个迁移执行者。在副本上按真实 revision 演练升级。新装默认 Weaviate 为 `1.39.2`；旧 `1.19.0` 等数据不能直接跳到该版本读取原卷。先按[向量库升级门槛](./容器镜像发布与多架构部署.md#旧-weaviate-升级门槛)和 runbook 在副本逐 minor 演练、备份及验证后，再决定目标部署。
4. 保持基础设施运行，完成初始化任务后执行上节 `migration` 服务。fork API / worker / beat 自动迁移固定关闭，不能以并发启动副本替代单执行者。
5. 双链及数据审计通过后，受控恢复业务、消费和调度，验收权限、模型、计费、知识库、插件、文件及工作流。

迁移失败时保留容器和日志，读取双版本表及已提交数据后决定恢复或重试。不要凭退出码盲目重跑，不要把 `downgrade` 当作数据恢复。回退需要匹配的旧镜像、配置和同一静止点的数据 / 存储，并处理新增写入。

自动生成的 `.dify_secret_key` 与存储一起备份；显式 `SECRET_KEY` 必须保留。多项目共享存储时串行初始化，不能并发 seed。密钥轮换按 [SECRET_KEY 轮换 runbook](./SECRET_KEY轮换runbook.md) 操作。

## 系统集成与权限

Console「系统管理」提供 Casdoor、钉钉、OAuth2 / 邮箱查询、用户余额和完整代码执行名单。页面及 API 校验初始化空间的真实数据库角色；其他空间的 owner / admin 不获得实例管理权限。切换空间、成员变化或初始化空间失效会改变权限，`RBAC_ENABLED=false` 和旧 `CASDOOR_CONFIG_ADMIN_ACCOUNT_IDS` 不能绕过该规则。

Casdoor SSO 使用配置草稿、静态校验、真实登录诊断及激活发布配置，自动发现签名公钥并验证登录结果。管理员填写组织、应用、Client ID / Secret、登录回调和默认空间等实际参数；Secret 加密保存且不回显明文。当前支持 `COMMUNITY` 且 `RBAC_ENABLED=false` 的 SSO 配置；Enterprise / RBAC 开启模式当前不支持激活。默认登录空间与实例管理权限独立。配置说明见 [Casdoor 配置指南](./Casdoor-SSO配置指南.md)，钉钉邮箱查询见[配置指南](./钉钉企业邮箱查询配置指南.md)。

## 构建与发布

正式发布流程为 [GitHub Actions `publish-dify-plus.yml`](../../.github/workflows/publish-dify-plus.yml)，构建 API、Web、Agent 后端及 Agent 本地沙箱的 amd64 / arm64 镜像并推送 GHCR。全部 8 组原生平台构建和组件冒烟通过、源码 revision 与 registry 架构核验一致后，才生成四组件 `1.17.1-plus.2` 版本标签；不发布 `latest`。步骤、权限、发布证据和架构范围见[容器镜像发布与多架构部署](./容器镜像发布与多架构部署.md)。GitLab 文件保留为历史 CCR 发布参考。

本地构建用于当前宿主平台验证，不能单独证明双架构发布。API、Web、Agent 后端以仓库根为上下文，Agent 本地沙箱以 `dify-agent-runtime` 为上下文：

```bash
# 从仓库根执行。
docker build -f api/Dockerfile -t dify-plus-api:local .
docker build -f web/Dockerfile -t dify-plus-web:local .
docker build -f dify-agent/Dockerfile -t dify-plus-agent-backend:local .
docker build -f dify-agent-runtime/docker/Dockerfile -t dify-plus-agent-local-sandbox:local dify-agent-runtime
```

[`docker-compose.local-build.yaml`](../../docker/docker-compose.local-build.yaml) 覆盖全部 API 消费者及其他三个组件。与主文件叠加后先检查配置，再构建四组件；按全新安装或升级步骤串行初始化与双迁移，不直接跳过数据库检查。该文件的本地标签用于验证，不替代 GHCR 发布证据。

Web 在对应架构的镜像构建阶段从锁文件安装依赖并生成 Next / Vinext 产物。不要将宿主机已有构建产物作为另一个架构的发布依据。发布记录包含源码提交、镜像 digest、双迁移版本、恢复信息和实际业务验收；CI 成功不等同于生产完成。

## 日常运维

```bash
# 从 docker 执行；自定义 override 保持与实际部署相同的文件组合。
docker compose -f docker-compose.dify-plus.yaml logs --tail=100 api worker worker-gaia worker_beat nginx
docker compose -f docker-compose.dify-plus.yaml exec api flask db current
docker compose -f docker-compose.dify-plus.yaml exec api flask extend_db current
```

| 现象 | 排查重点 |
| --- | --- |
| 编辑器遮罩不消失、节点无法点击 | 协作 profile、Socket URL、`/socket.io/` 反代和 worker 类；验证 101 与真实操作 |
| 工作流完成但余额未更新 | `worker-gaia` 的 `extend_high` 消费、计费失败、usage / 付款账号归因 |
| 索引持续排队 | `dataset` / `priority_dataset` 消费者、Redis、数据库及存储 |
| 调度或额度未重置 | `worker_beat`、扩展开关、实际投递和消费 |
| API 重建后入口 502 | API 健康、nginx 服务名解析、网络及已加载配置 |
| SSE 或旧页面异常 | 流式 POST 与 Service Worker；清理旧站点缓存后复核 |

文档修复工具会修改数据库、Redis 或投递任务；先定位故障、核对范围及备份，使用匹配运行环境：

| 脚本 | 用途 |
| --- | --- |
| `scripts/fail_pending_documents.py` | 暂停排队或执行中的文档 |
| `scripts/fix_stuck_documents.py` | 根据段落实际状态处理卡住索引 |
| `scripts/rerun_document_indexing.py` | 按名称 / ID 重置并重提索引 |
| `scripts/run_and_stop_dataset_tasks.py` | 批量运行或停止任务 |

后端命令通过 `uv run --project api <command>` 执行，例如从仓库根运行 `uv run --project api python scripts/rerun_document_indexing.py <文档ID>`。名称搜索可能匹配多个文档，无参数也可能作用于全部异常文档，先核对实际选择。基础设施故障应先恢复再处理索引状态。

## 工作流运行记录归档

工作流冷备使用 `api/commands/retention.py` 的命令与 `api/services/retention/workflow_run/` 实现。配置独立的 S3 兼容归档存储：`ARCHIVE_STORAGE_ENABLED`、`ARCHIVE_STORAGE_ENDPOINT`、`ARCHIVE_STORAGE_ARCHIVE_BUCKET`、`ARCHIVE_STORAGE_EXPORT_BUCKET`、`ARCHIVE_STORAGE_ACCESS_KEY`、`ARCHIVE_STORAGE_SECRET_KEY`、`ARCHIVE_STORAGE_REGION`；验证实际挂载和环境映射。归档 bucket 与导出 bucket 分别保存长期 bundle 和下载产物。

| 命令 | 用途 |
| --- | --- |
| `archive-workflow-runs-plan` | 估算指定时间窗口及空间范围 |
| `archive-workflow-runs` | 写入 V2 Parquet bundle、manifest 和索引 |
| `backfill-workflow-run-archive-bundles` | 根据 manifest 回填数据库索引 |
| `restore-workflow-runs` | 校验 bundle 并恢复记录 |
| `delete-archived-workflow-runs` | 独立校验后删除源数据 |

先查看命令实际参数，再按选定空间和固定 UTC 绝对时间窗口规划；预览与归档使用同一窗口，避免分片执行中相对时间漂移。示例仅查看帮助，不执行数据操作：

```bash
# 从仓库根，在具有后端配置和基础设施的环境执行。
uv run --project api flask --app api/app.py archive-workflow-runs-plan --help
uv run --project api flask --app api/app.py archive-workflow-runs --help
uv run --project api flask --app api/app.py restore-workflow-runs --help
uv run --project api flask --app api/app.py delete-archived-workflow-runs --help
```

归档成功需要对象与索引写入完成，归档不会自动删除源记录；删除必须单独校验。恢复前保存当前数据恢复点，核对空间、运行与源数据范围。自托管 CLI 的租户过滤不要求 Cloud 付费计划；Cloud 部署按 Professional / Team 筛选。Console 月度列表、下载任务和 ZIP API 仍限定 Cloud 付费计划，不代表自托管有相同页面入口。

旧[批量工作流业务表冷备](./批量工作流数据表冷备归档说明.md)是历史数据方案，与当前工作流运行日志归档不同。
