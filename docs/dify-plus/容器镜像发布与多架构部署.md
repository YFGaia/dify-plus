# 容器镜像发布与多架构部署

容器发布版本为 **`1.17.1-plus.2`**，源码基线仍为 Dify 社区版 `1.17.1`。本次交付将 API、Web、Agent 后端和 Agent 本地沙箱统一发布到 GitHub Container Registry（GHCR），目标平台为 `linux/amd64` 和 `linux/arm64`。这里的兼容指 CPU 架构，不表示一个镜像可跨任意 Dify 版本或读取任意旧数据库。

**发布状态：本文件记录发布配置与验收门槛。尚未附上成功的 `release-evidence`、四组件 registry digest 和目标环境验收结果前，不将 `1.17.1-plus.2` 稳定标签视为已验证可用。** Compose 默认值和源码提交本身不证明镜像已发布。`1.17.1-plus.1` 保留为既有[源码发布](./releases/1.17.1-plus.1.md)，不重指该 Git tag，也不覆盖历史发布事实。

## 实施与发布顺序

1. 固定经过审查的源码提交、锁文件、Dockerfile 与 Compose。所有组件使用同一源码 revision，禁止把未提交文件或宿主机旧产物当作已推送源码。
2. 在两个原生 Linux runner 上分别构建四组件，共 8 组；在各自平台实际启动或运行组件冒烟检查。
3. 仅通过冒烟的构建推送架构候选标签；聚合 8 份证据，核验 GHCR 返回的架构和源码 revision。
4. 生成四组件多架构候选与版本标签，保存 index / 子 manifest digest 和发布清单；稳定标签已有不同 revision 时拒绝覆盖，不发布 `latest`。
5. 核对完整 Compose 实际启用的基础设施和目标架构。单执行者完成密钥初始化和双迁移，在隔离环境验证业务，已有环境另完成恢复与向量库升级演练。
6. 目标部署记录完整配置组合、不可变镜像、备份、迁移结果、业务验收及回退路线。镜像发布与生产部署分别签收。

## 部署镜像变量

主入口为 [`docker/docker-compose.dify-plus.yaml`](../../docker/docker-compose.dify-plus.yaml)。镜像覆盖参考位于 [`docker/envs/dify-plus-images.env.example`](../../docker/envs/dify-plus-images.env.example)，按需将参数复制到 `docker/.env`；该参考文件不会被 fork Compose 自动加载。四组件默认 `1.17.1-plus.2`，可在 `docker/.env` 中覆盖为已验证版本或 `名称@sha256:...`：

| 变量 | 默认镜像 |
| --- | --- |
| `DIFY_PLUS_API_IMAGE` | `ghcr.io/yfgaia/dify-plus-api:1.17.1-plus.2` |
| `DIFY_PLUS_WEB_IMAGE` | `ghcr.io/yfgaia/dify-plus-web:1.17.1-plus.2` |
| `DIFY_PLUS_AGENT_IMAGE` | `ghcr.io/yfgaia/dify-plus-agent-backend:1.17.1-plus.2` |
| `DIFY_PLUS_LOCAL_SANDBOX_IMAGE` | `ghcr.io/yfgaia/dify-plus-agent-local-sandbox:1.17.1-plus.2` |

用发布清单中的多架构 index digest 固定镜像，Docker 会选取当前平台子 manifest。需要指定平台时独立保留子 manifest digest；不可把 amd64 子 digest 当作通用双架构 digest。不要强制 `platform: linux/amd64` 掩盖 ARM64 供应缺失。

本地参考为 [`docker-compose.local-build.yaml`](../../docker/docker-compose.local-build.yaml)，覆盖四组件及全部 API 消费者。构建验证步骤：

```bash
cd docker
# 已准备 .env 并填写 DIFY_AGENT_SERVER_SECRET_KEY；已有环境先完成升级准备。
docker compose -f docker-compose.dify-plus.yaml -f docker-compose.local-build.yaml config --quiet
docker compose -f docker-compose.dify-plus.yaml -f docker-compose.local-build.yaml build api web agent_backend local_sandbox
```

后续初始化、双迁移和业务启动均保留同一文件组合，按[部署指南](./二开部署配置与运维说明.md)逐步执行。`config --quiet` 用于配置校验；完整 `config` 会展开部署凭据，不应公开或提交。专用扩展与索引消费者分别使用 `DIFY_PLUS_EXTEND_CELERY_QUEUES` 和 `DIFY_PLUS_DATASET_CELERY_QUEUES`，不要用主 worker 队列变量覆盖全部消费者。

## 基础设施与供应边界

四组件发布不包含基础设施镜像重构建。部署前从实际 Compose 的启用 profiles 得到镜像清单，逐项核验可拉取性、目标架构与配置兼容。基础设施来源和新装基线如下，精确 digest 由具体发布/部署记录固定：

| 服务 | 来源 / 版本 | 验证要求 |
| --- | --- | --- |
| `init_permissions` | Docker Hub `busybox:1.37.0` | 初始化命令与共享卷权限 |
| `db_postgres` / `db_mysql` | Docker Hub `postgres:15-alpine` / `mysql:8.0` | 选择实际数据库 profile；双迁移与恢复 |
| `redis` | Docker Hub `redis:6-alpine` | 密码、broker 和队列一致 |
| `nginx` | Docker Hub `nginx:1.28.0`（Debian；现有入口使用 Bash） | 反代、SSE、Socket.IO 101 与真实节点点击 |
| `ssrf_proxy` / `agent_ssrf_proxy` | Docker Hub `ubuntu/squid:6.6-24.04_edge` | 两个代理的目标架构、配置、上游及连通性 |
| `sandbox` | Docker Hub `langgenius/dify-sandbox:0.2.15` | 普通代码执行与认证 |
| `plugin_daemon` | Docker Hub `langgenius/dify-plugin-daemon:0.6.10-local` | 实际插件安装、执行、持久目录与 API 认证 |
| `weaviate` | `cr.weaviate.io/semitechnologies/weaviate:1.39.2` | 新装基线；HTTP / gRPC、索引、检索与恢复 |
| `sandbox-full` | 默认 `ccr.ccs.tencentyun.com/yfgaia/dify-plus-sandbox-full:1.2.2` | 可选供应镜像，无本仓构建源码；独立验证架构和完整代码执行 |
| 其他向量库 / `certbot` / `unstructured` | 各自 profile 的 Compose 镜像 | 按实际启用组合逐项验证，默认部署结果不覆盖所有 profile |

默认 profiles 为 `weaviate,postgresql,collaboration`。2026-10-07 的[基础设施 manifest 核验记录](./releases/1.17.1-plus.2-dependencies.json)包含这些默认供应镜像及可选完整沙箱的 index digest 与两架构结果；它只证明 registry 平台供应，不替代运行验收。将数据库或向量库改为其他 profile 后，需核对实际服务、网络和对应镜像；未验证的可选组合不自动获得双架构部署结论。Tag 随上游更新可能变化，目标部署必须固定验证过的 digest。

### 可选完整沙箱

`sandbox-full` 通过 `full-sandbox` profile 单独启用；默认安装不启动该服务。需要完整代码执行时，先核验供应镜像、认证及网络，再把 `full-sandbox` 加入实际 `COMPOSE_PROFILES`，并通过 `DIFY_PLUS_FULL_SANDBOX_IMAGE` 指定已验证镜像。`FULL_CODE_EXECUTION_ENDPOINT` 应指向可访问的完整沙箱，所有 API 消费者使用一致配置。

代码授权按当前工作空间 owner 邮箱匹配。默认 profile 未启动完整沙箱时，不要为工作空间启用完整代码执行授权，否则匹配后的执行会访问未运行服务。供应 registry 的双架构 manifest 只证明存在两个平台镜像，不证明完整执行能力；本次 GHCR 四组件构建不能代替该供应镜像的运行验收。

### 旧 Weaviate 升级门槛

`1.39.2` 是新装基线。已有部署先盘点真实版本、数据目录、节点数和备份，不能直接将旧 `1.19.0` 卷挂给新默认镜像，也不能通过回退镜像读取已经变更格式的目录。

在隔离副本中一次升级一个 minor，并使用各 minor 已核验的 patch；跨越 `1.25` 时验证 Raft 元数据迁移，跨 `1.26` 及后续版本前检查节点统计与 `synchronized` 状态。旧 `1.19` 及更早版本另核对历史迁移指南。官方规则见 [Weaviate Migration and Upgrades](https://docs.weaviate.io/deploy/migration)。

每站 graceful stop、重新启动后记录 schema、对象与向量数量、固定查询集、索引写入及备份恢复。关键阶段保存新的一致恢复点；失败停止推进，使用匹配的镜像、配置与数据恢复。原位路径无可靠证据时单独评估逻辑导出、重建和重新索引。具体环境路径及生产门槛沿用[升级与恢复 runbook](../../openspec/changes/merge-upstream-1-17-1/runbook.md)，不把镜像发布当作旧库演练完成。

## GitHub Actions 与 GHCR 操作

工作流为 [`publish-dify-plus.yml`](../../.github/workflows/publish-dify-plus.yml)。通过 `workflow_dispatch` 输入 `release_version`（默认 `1.17.1-plus.2`），或推送符合 `1.*-plus.*` 的 Git tag 触发。手工发布应选择已经推送、审查且包含该工作流的源码 ref。工作流须已注册在默认分支才能接受手工触发；规则见 [GitHub workflow_dispatch 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)。

原生 runner 为 `ubuntu-24.04` 和 `ubuntu-24.04-arm`，避免用模拟架构构建替代原生冒烟。工作流使用 `GITHUB_TOKEN` 和 `packages: write`，无需 Docker Hub 或 CCR 发布凭据。已有同名 GHCR Package 时核对它是否关联当前仓库及授权该仓库 Actions；首次发布默认可能是 private，需设置所需可见性并验证公开匿名拉取。私有部署使用具备 `read:packages` 的用户凭据。具体权限见 [GitHub Container registry 文档](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)。不要将 token 写入 Compose、文档或构建上下文。

从 GitHub Actions 页面选定源码 ref 并运行即可；已登录 GitHub CLI 的发布者也可执行：

```bash
# SOURCE_REF 为已经推送、审查并包含工作流的分支或 tag。
: "${SOURCE_REF:?请先指定已审查源码 ref}"
gh workflow run publish-dify-plus.yml --repo YFGaia/dify-plus --ref "$SOURCE_REF" -f release_version=1.17.1-plus.2
gh run list --repo YFGaia/dify-plus --workflow publish-dify-plus.yml
```

等待选定 run 的所有构建及发布阶段成功，再从该 run 下载 `release-evidence`。失败时检查具体组件/架构日志，修复后发布新的已审查 revision；不同 revision 不覆盖已有稳定版本。仅有部分架构 candidate 不算完整发布。

## 发布证据与验收边界

架构候选为 `sha-{完整40位源码SHA}-{amd64|arm64}`，多架构候选为 `sha-{完整40位源码SHA}`。组件证据 artifact 为 `image-evidence-{component}-{arch}`；最终 `release-evidence` 中的 `release-manifest.json` 记录 `release_version`、`source_revision`、四镜像 index digest、两架构子 digest 与组件冒烟范围。

| 证据层 | 要保存的结果 | 能证明的范围 |
| --- | --- | --- |
| 源码与构建 | 提交、锁文件、Dockerfile、原生平台构建结果、OCI source / revision | 可复现源码身份及构建平台 |
| 组件冒烟 | API 依赖/源文件、38 provider 元数据和32 entrypoint 装载、隔离 PostgreSQL 双迁移与 API 启动；Web 启动及 `/signin`；Agent 启动及 `/openapi.json`；本地沙箱 `/healthz` | 本架构组件依赖与启动契约，不覆盖所有业务 |
| Registry | 四 index digest、8 子 manifest、平台与 revision 读回、拉取权限 | GHCR 已发布与架构选择；不等于生产运行 |
| 部署与数据 | 实际完整 Compose、profiles、服务镜像、双 revision、配置与存储恢复 | 被验证部署组合及数据路径 |
| 业务 | 权限/登录、真实模型、余额/Key、知识库/插件、Socket.IO 与 Agent 执行 | 实际执行范围；外部供应商需真实配置和回执 |

部署方按发布清单逐个核对四组件，示例查看 manifest：

```bash
docker buildx imagetools inspect ghcr.io/yfgaia/dify-plus-api:1.17.1-plus.2
docker buildx imagetools inspect ghcr.io/yfgaia/dify-plus-web:1.17.1-plus.2
docker buildx imagetools inspect ghcr.io/yfgaia/dify-plus-agent-backend:1.17.1-plus.2
docker buildx imagetools inspect ghcr.io/yfgaia/dify-plus-agent-local-sandbox:1.17.1-plus.2
```

输出必须包含 `linux/amd64` 和 `linux/arm64`，并与发布清单 digest 对应。生产还需自己的 SSO、模型、插件和数据验证。HTTP 200、容器 healthy、零 token 工作流、构建或 registry 成功都不能替代完整业务验收。缺少旧库升级、供应镜像运行或外部服务证据时，在发布记录中单列未完成项。
