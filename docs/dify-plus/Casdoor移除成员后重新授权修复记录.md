# Casdoor 移除成员后重新授权修复记录

本记录对应 2026-10-07 的本地问题排查与验收，不代表生产部署或其他外部身份环境已验收。

## 实际根因

失败页显示“权限更新尚未完成”。截图关联 ID 在数据库中对应一条已提交的 profile 同步审计；Casdoor 令牌验证、用户与角色查询成功。没有待处理的必需权限任务。

1. 该成员此前从 Dify 空间移除，托管历史保留旧成员 ID，变为 `local_override` 且 `tombstone=true`。登录持久化保留这个移除状态，收尾校验发现目标空间没有成员记录，拒绝签发会话。
2. 管理员角色映射只存在于配置草稿 v9；当时生效的 v8 映射为空。普通登录使用生效版本，因此仍然走默认普通成员回退。仅在 Casdoor 添加角色或在 Dify 保存草稿，均不会让草稿映射立即生效。

## 修复规则

- 仅同一命名空间和身份绑定、此前移除的本地托管成员，在新的认证与在线角色查询命中当前生效配置的显式角色映射时，允许重新加入对应空间，包含默认登录空间。
- 恢复沿用现有成员写入、完整事务、锁、整行条件更新与审计流程；创建新的成员记录，恢复托管状态并清除移除标记，保留原历史记录、托管基线和身份绑定。
- 默认普通成员回退、现存人工角色覆盖、owner、已释放关系、其他命名空间历史及必需权限任务继续保留原有保护。
- 文本日志现在包含安全的操作名、结果代码和关联 ID；仍不记录异常正文、令牌或原始身份响应。

## 本地交付与回滚

本地修复镜像为 `difyplus-casdoor-api:mapped-regrant-20261007`，保留原镜像 `difyplus-casdoor-api:initial-scope-20261007`。镜像构建与追加 Compose 覆盖文件保存在 `/private/tmp/dify-casdoor-regrant.Dockerfile` 和 `/private/tmp/dify-casdoor-regrant.compose.yaml`；覆盖文件是在原有三个 Compose 配置之后追加使用，原有未跟踪的开发覆盖文件未修改。

仅更新本地 API、WebSocket 和 worker 服务，没有数据库迁移，没有重置数据卷，也没有直接修改成员数据库记录；实际恢复由成功登录事务完成。后续若只使用原三个 Compose 文件重建服务，会选择旧后端镜像；应保留追加覆盖文件，或通过正常发布流程构建包含修复的后端镜像。

需要回滚代码时，可用原三个 Compose 文件重建上述常驻后端服务；已启用的映射和已恢复成员不应随代码回滚被清除。配置回滚需通过原生版本校验与启用流程单独处理。完成本地验收后，按用户要求提交源码并推送 GitHub；未创建分支或工作树，未执行发布。
