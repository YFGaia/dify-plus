# N05 nonzero billing acceptance design (read-only source analysis)

No provider secrets, prices, balances, or application data were read/changed for this analysis. No new source regression is established by this review.

1. **Find a billable model before making another call.** The graphon 0.7.0 model runtime `AIModel.get_price()` returns zero USD when model schema pricing/input-output rates are absent. Otherwise it computes `tokens * unit_price * unit`, rounding each price to 7 decimal places. The previous DeepSeek V4.1 Flash run was successful but stored 0 USD; zero usage price cannot exercise positive debit. Inspect only the installed plugin's static model definitions or safe schema `pricing` fields. Use an already authorized, supported stock model with nonzero official/plugin pricing. Do not invent a local rate or rewrite old usage to manufacture a passing debit. If no such model is available, N05 positive pricing remains blocked with that exact evidence.

2. **Observe the correct consumer and charge owner.** Chatflow/Workflow use `WorkflowPersistenceLayer._handle_node_succeeded()` -> `update_account_money_when_workflow_node_execution_created_extend.delay()` on **extend_high**. A worker consuming only workflow execution can finish the app while leaving billing queued. Verify both workflow execution and extend_high queues. The task intentionally exits before database access when `usage.total_price == 0`; positive usage atomically increases personal used_quota and, when a workflow-run/token join exists, accumulated/day/month key usage. Easy UI chat/completion charge via message-created signal instead. There is no duplicate message-created signal in Chatflow's current pipeline.

3. **Personal debit minimal test.** In an authorized disposable acceptance workspace, retain one simple Start -> LLM -> Answer flow with max output tokens <=64 and reasoning off if that stock model supports it. Record the scoped account's used_quota in full 7-decimal USD precision, execute one small prompt, await succeeded run and billing completion, then compare `delta_used_quota == sum(node usage converted to USD)`. Conversion is direct for USD and divides by the configured RMB_TO_USD_RATE otherwise. Avoid other model requests, automatic title-generation charges, retries/resumption, or concurrent users during the measurement. The rounded UI badge is insufficient; prove run/message/node/owner and the full-precision account row. Existing schema precision is 1e-7 USD.

4. **App API key positive debit and bounds.** Use one disposable app key via existing UI/service boundaries; handle its generated secret only in memory and never print it, include headers in logs, or read user-owned keys. For one successful call, assert a single `ApiTokenMessageJoinsExtend` row binds the real app token ID to the message/workflow run, and positive `accumulated_quota`, `day_used_quota`, `month_used_quota` all increase by the same normalized charge. Personal payer is the active app tenant's owner, through the end-user/account mapping. daily/monthly -1 means unlimited; 0 or used >= limit rejects before model invocation with 403. `accumulated_quota` is cumulative usage, not a lifetime cap. Do not change the user's existing balances/limits. Boundary tests requiring limit manipulation belong only to a disposable key/workspace or source unit tests.

5. **Keep known debts visible.** Existing message handler account update is read/modify/write; workflow task has retries but no durable debit-idempotency key. P4 is separately planned. A single controlled positive-debit run verifies the merge path, not concurrency/at-least-once financial correctness, and must not mark all six billing chains passed.
