# M06 12.6e review follow-up

## Findings and closure

The initial independent Luna review identified two P2 defects in commit `e9359f9bfe688f24212112cdc3e5f2ac6560c910`:

1. Dual-write SQL scope validation could swallow non-`ValueError` failures and append a Logstore version without validating tenant/app scope.
2. The extension migration returned when the ownership table already existed, even if the required scope index was missing.

Commit `2ca9e0d7cbb3b1cc79148d44659129cf84f98451` closes both findings. The Logstore repository now lets every `validate_scope` exception stop the append and propagate; its outer exception handler records the traceback. The later SQL backup remains best-effort after a successful Logstore append. The migration now checks for the named scope index when the table exists, creates a missing index, and tolerates a missing table or index during downgrade.

Independent diff-only Luna conversation `01a0ebaf-7f96-7112-815c-33ef98a6a395` found no P1 or P2 and did not independently rerun tests. It noted that a same-named index with an incorrect column definition is treated as present, which could degrade query performance but would not change query results. A second repo-context Luna review `01a0ebae-0dd2-70b3-a0cb-2cf9e483d45e` inspected the surrounding implementation and tests and found no P1/P2/P3; it confirmed the outer Logstore exception handler records validation failures. This theoretical index-drift case is not a confirmed defect and is recorded as a bounded performance consideration. In offline `as_sql` mode, Alembic cannot inspect database state, so emitted DDL follows the migration sequence and is not an idempotent repair script for an unknown preexisting schema. Online behavior depends on the active SQLAlchemy dialect's `get_indexes()` reporting the named index correctly.
