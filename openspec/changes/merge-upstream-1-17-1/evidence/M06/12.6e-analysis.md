# M06 12.6e workflow account actor path analysis

Analysis conversation: Sol `01a0eb7c-8d27-70e0-acf6-70764808b6a0`, read-only.

## Source findings

The first loss of trusted identity occurs when the workflow execution repository is constructed. Console admission supplies `RequestContext.account_id`; the WebApp route separately validates the current Console cookie and puts its account ID in request args/extras. The workflow generator constructs the execution repository with only the EndUser. SQLAlchemy and Logstore then persist the EndUser as `created_by`, which represents the workflow actor and must not be overwritten with the Console account.

Persist the actor only from a Console `Account` validated for this request. Anonymous or un-attributable historical executions have no ownership record, and personal queries exclude them. Never infer or backfill from `EndUser.external_user_id`. Keep `created_by_role/created_by` unchanged.

Safe scope for this change: attribute WebApp runs only when the current request's Console cookie resolves to a valid account. Do not infer ownership for other `APP_RUN` entry points. Preserve the field through any configured Celery execution repository and both normal and async recovery so a later save cannot erase the original actor. Existing app-wide queries remain unchanged.

### Migration boundary correction

`api/migrations_extend/README.md` limits the extension migration chain to Dify Plus extension tables and explicitly says it does not alter original system tables. `WorkflowRun` maps the upstream-owned `workflow_runs` table, so attaching a migration to the extension chain does not make adding a column to that table compliant.

Persist SQL-backed ownership in a new `workflow_run_account_extend` table, keyed by `workflow_run_id` and scoped with `tenant_id` and `app_id`. Create it as revision `020_workflow_run_account` after `019_webapp_auth_switch`; keep the upstream `workflow_runs` model and migration chain unchanged. Store only an authenticated WebApp Console account ID. Existing runs and anonymous runs have no association row, so they remain unattributed. SQLAlchemy run writes and association writes must share a transaction; reads must validate tenant/app scope. Logstore runs retain their trusted actor in their own event fields; reads and recovery must not require a SQL association lookup. If configured SQL dual-write is enabled, write the fork association row in the same SQL transaction. No historical backfill or inference is allowed.

The first Astra implementation draft added a column to the upstream model and was stopped before commit. That draft is not accepted. The restarted implementation must use the extension association table and update the registered paths below.
