## Evidence and resulting behavior

The pre-merge fork at `b17761ed0166e8ef49474da418b95a9462adbb9c` had a workspace-manager gate in `web/app/components/develop/secret-key/secret-key-button.tsx`: it read `isCurrentWorkspaceManagerAtom` and returned null for non-managers. Its `canManage` prop separately disabled the trigger. The new Access Point button previously checked only `canManage`; this lost the explicit workspace role boundary when an app ACL allowed a non-manager.

The current `web/context/workspace-state.ts` exposes the same role atom. Its source is the validated current workspace summary; `getWorkspaceRoleFlags` in `web/context/app-context-normalizers.ts` identifies owner/admin as managers.

The button now derives `canManageApiKeys = isCurrentWorkspaceManager && canManage` and applies that permission to its generated App Key query, disabled state, and modal boundary. Non-managers retain the fork's hidden entry behavior, including environment-scoped entries. A manager still needs the caller's current Access Point ACL. App Key queries use `skipToken` when unauthorized; the environment entry continues to receive its count from the caller and does not issue the App Key query.

The management subtree exists only while both permissions hold. Revoking either permission removes any open key-management subtree, including nested confirmation/editor dialogs. Ordinary open/close state still uses the existing controlled modal lifecycle. The shared `ApiKeyModal` implementation and dataset caller were not changed.

## Test changes and validation handoff

The focused RTL spec retains the existing allowed environment, disabled service, and ACL rejection cases. It now uses the real workspace summary and role atom, with only the Console transport and independently owned modal mocked. The transport mock preserves the `ClientLink.call(path, input, options)` boundary; the allow case starts without cached keys and observes one request, so denial checks cannot pass merely because a seeded key result suppresses all transport.

The resulting spec contains 9 cases:

- owner and admin with Access Point permission can request App Keys and open management (2 cases);
- an allowed manager can open environment-scoped management;
- service-disabled state retains the visible count and disabled trigger;
- a manager without Access Point permission cannot request or open keys;
- an editor with Access Point permission cannot request keys or render/open management for App or environment scope (2 cases);
- revoking workspace-manager identity or Access Point permission removes already open management (2 cases).

No tests were run by the implementation agent; Luna owns independent verification. Broader modal tests remain necessary to validate the actual quota/CRUD child behavior, which is outside this mocked button-owner spec. Backend, database, deployment, and production acceptance are outside this implementation evidence.

The two files were formatted with the existing Vite+ binary using Node 24.20.0 and `VP_SKIP_INSTALL=1`; no dependency installation occurred. Direct `oxfmt` invocation reported that its wrapper only supports IDE use, then `vp fmt` completed for the two exact paths. `git diff --check` passed for those paths.
